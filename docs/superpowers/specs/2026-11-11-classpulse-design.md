# ClassPulse 設計書（全体の段階分けと、試作1 の設計）

作成日: 2026-11-11　／　もとにした資料: `ClassPulse_要件定義書_v1.1_UIUX統合版.md`（以下「要件定義書」）

この設計書は、要件定義書の全体を段階に分け、最初の段階（試作1）で作るものを決める。試作1 の実装計画は、この設計書の承認後に別のファイルとして書く。

「ユーザーの決定」と書いた項目はユーザーが会話で決めたこと。「Claude の判断」と書いた項目は Claude Code が決めたことで、ユーザーは変更できる。

## 1. 目的

先生がスライドを映して授業を進めながら、生徒が自分の端末でアンケートに答え、結果をその場で一緒に見られるようにする。

試作1 が成功した状態（ユーザーの決定）:

- 30 人ほどの 1 学級の授業で使える。
- 先生は iPad で操作し、その iPad をミラーリングして生徒に映す。
- 生徒は iPad で QR コードを読んで参加し、「〇〇は好きですか？ はい／いいえ」のような選択式アンケートに答える。
- 先生と生徒が、集まった結果をその場で見て確かめながら授業を進める。

## 3. 試作1 に入れるもの・入れないもの

### 入れるもの

- 先生のログイン（メールアドレスとパスワード）。登録されている先生だけが使える。
- 教材の一覧（授業ダッシュボード）: 新規作成、編集、発表を開始、結果を見る、削除。
- スライドの編集: スライドの追加・削除・順番変更、文字と画像の配置、選択式アンケートのスライド、自動保存（保存中・保存済み・保存失敗の表示）。
- 発表: QR コードとリンクの表示、前へ・次へ、参加人数と回答数、結果の表示・非表示、回答受付の停止、授業の終了。
- 生徒の画面: QR コード・リンクから参加（ログインなし）、先生の進行への自動追従、選択式アンケートへの回答と変更、送信状態と通信状態の表示、終了画面。
- 授業結果の閲覧: 授業ごとに、質問ごとの選択肢別の件数と割合をアプリ内で見る。
- 要件定義書 7 章の配色・余白・角丸・UD フォント（BIZ UDPGothic）。

### 入れないもの（後の段階）

- PowerPoint・Google スライドの取込み（ユーザーの決定: 軽い方として、アプリ内での作成を先にする）。
- 選択式以外の回答 4 種類、記名回答、投稿の承認、不適切な表現の自動検出。
- PDF・Excel・CSV 出力、ゴミ箱と復元、Google Drive 連携、Google アカウントでのログイン、管理者の画面。
- 動画・音声、アニメーション、図形の描画。
- 200 人の同時回答の検証。

### してはいけないこと

- 結果を非公開にしている間に、先生の発表画面（生徒に映っている）へ結果を出す。
- 生徒の回答に名前や、名前と結びつく情報を付けて保存する。
- 前のスライドに戻ったときに、回答の受付を再開する（または再開したように見せる）。
- 要件定義書 8 章と付録 A で「採用しない」とされたもの（参加コードの入力、共同編集、タイマー、通知など）を足す。

## 4. 作り方の土台

### 4.1 これまでのアプリと同じにするところ（ユーザーの決定: 今までの作り方を参考にする）

時間割アプリ・理科アプリと同じ進め方にする。

- フォルダ: `C:\Users\yan12\Documents\keita\AI開発\スライドアプリ`。Git リポジトリにする。
- `CLAUDE.md` と `AGENTS.md` を理科アプリのものをもとに置く（Claude Code が設計と指示書、サブエージェントが実装、Codex がレビュー。Codex が使えないときは別の Claude エージェントがレビュー）。
- 実装指示書は `.ai-tasks/`、レビュー結果は `.ai-review/`。`tools/codex-implement.ps1` と `tools/codex-review.ps1` を理科アプリからコピーして使う。
- 要件定義書を `docs/requirements.md` に置く（原本はそのまま残す）。
- HTML・CSS・JavaScript だけで書く。ビルドの工程とパッケージのインストールを使わない。
- ロジックは `node --test` で確かめる（`npm test`）。画面はブラウザで確かめる。
- iPad の Safari を基準にする（ユーザーの決定: 先生も生徒も iPad）。

### 4.2 これまでと違うところ（Claude の判断）

- **サーバー側の保存と通信に Firebase を使う。** 理科アプリのライブクイズと同じく、Realtime Database を REST と EventSource で使う（Firebase の SDK は入れない）。無料枠（Spark プラン）の範囲で使う。課金の設定はしない。
- **Firebase Authentication を使う。** 理科アプリのライブクイズは「部屋コードを知っていればだれでも書きこめる」作りだったが、ClassPulse は先生ごとのデータの分離と、生徒が他人の回答を書きかえられないことが要る。
  - 先生: メールアドレスとパスワードでログイン（REST の `signInWithPassword`）。先生のアカウントは、管理者（ユーザー本人）が Firebase のコンソールで作る。アプリに「新規登録」の画面は作らない。これで「招待された先生だけ」を満たす。
  - 生徒: 画面には何も出さず、匿名のログイン（REST の `signUp`）で端末ごとの ID をもらう。この ID は名前と結びつかない。
  - ログインの期限（1 時間）が切れる前に、更新用のトークンで自動的に更新する。
- **通信の部分を 1 つのモジュールにまとめる。** 画面やロジックは Firebase の URL や書式を直接知らない。学校のネットワークから Firebase につながらなかった場合に、このモジュールだけを別の仕組みに差しかえられるようにする。
- **画像はデータベースに入れる。** Firebase Storage は無料枠で新しく使えないため、画像は端末で縮小（長辺 1280px、JPEG、1 枚およそ 200KB まで）してから Realtime Database に保存する。1 教材の画像は合計 5MB までとし、超えるときは画面で知らせる。
- **QR コードの生成**は、ライセンスが MIT の小さな JavaScript ファイルを 1 つリポジトリに入れて使う（外部の配信元から読み込まない）。
- **フォント**は BIZ UDPGothic の通常・太字の woff2 をリポジトリに入れて配信する。`font-display: swap` で、読み込み中は端末の日本語書体で表示する。OFL のライセンス文を一緒に置く。
- **公開**は GitHub Pages（理科アプリと同じく `pages` ブランチ）。https が必要（iPad のカメラで読んだ QR コードから開くため）。
- Service Worker によるオフライン対応は、試作1 では入れない（段階 5）。

### 4.3 ユーザーにお願いする作業

- Firebase のプロジェクトを新しく作り、Realtime Database と Authentication（メール／パスワード、匿名）を有効にし、規則（リポジトリの `docs/firebase/rules.json`）を貼る。手順書（`docs/firebase/setup.md`）を用意する。
- Firebase のコンソールで、自分の先生アカウントを 1 つ作る。
- GitHub に新しいリポジトリを作り、Pages を有効にする。
- 段階 0 の確認ページを、学校の iPad で学校のネットワークから開く。

Firebase の設定値（データベースの URL と Web API キー）は `js/firebase-config.js` に書く。この 2 つは公開してよい値で、データを守るのは規則である。パスワードなどの秘密はリポジトリに入れない。

## 5. 画面

画面は 1 つの `index.html` の中で切りかえる（URL の `#` 以降で画面を決める）。生徒が開くのは `#/join/<授業ID>` だけ。

### 5.1 ログイン（先生）

メールアドレスとパスワードの入力欄と「ログイン」。まちがえたときは文字で理由を出す。新規登録の案内は出さない。

### 5.2 授業ダッシュボード

要件定義書 7.5 A の配置をもとにする。

- 左: ナビゲーション（ホーム、授業履歴、設定）。iPad の縦向きやスマートフォンでは上部のメニューに畳む。試作1 で作らない項目（ゴミ箱など）は出さない。
- 中央: 教材のカードの一覧。カードごとに「編集」「発表を開始」「結果を見る」「削除」。
- 上部: 「新規作成」と、ログイン中の先生のメールアドレス、「ログアウト」。
- 削除は確認を出す。試作1 にはゴミ箱がないので、確認の文に「元に戻せません」と書く。

### 5.3 スライド編集

要件定義書 7.5 B の 3 列（左: スライド一覧、中央: キャンバス、右: 設定）をもとにする。iPad の縦向きでは、スライド一覧と設定を開閉できるパネルにする。

- スライドの種類は 2 つ: **資料スライド**と**アンケートスライド**。
- 資料スライド: 16:9 のキャンバスに、文字の箱と画像を置く。指でドラッグして動かし、角のつまみで大きさを変える。文字は大きさ（小・中・大・特大）、太字、色（7.2 の配色から）、左・中央・右のそろえを選べる。新しい文字の箱の書体は BIZ UDPGothic。
- アンケートスライド: 質問文、選択肢（2〜6 個。A〜F の記号が自動で付く）、「結果の出し方」（すぐ表示／先生が表示するまで出さない）。匿名であることを設定欄に書く（試作1 では切りかえなし）。
- スライド一覧: 追加（資料／アンケート）、削除、上へ・下へ（順番変更）、複製。
- 上部: 教材名（その場で書きかえ）、保存状態（「保存中」「保存済み」「保存できませんでした（再試行）」）、「発表を開始」。
- 自動保存: 変更の 1 秒後に保存する。保存に失敗したら、変更を端末に残したまま再試行し、画面に状態を出す。

### 5.4 発表（先生の iPad。そのまま生徒に映る）

ユーザーの決定により、先生の iPad の画面がミラーリングで生徒に見える。このため、発表画面には「映って困るもの」を出さない。先生だけに見せる画面は作らない。

- 中央に今のスライドを大きく出す。
- 下に操作の帯: 「前へ」「次へ」、現在位置（3 / 12）、参加人数、「QR コード」、「授業を終了」。「授業を終了」は「次へ」から離して置き、色（#E8576A）と文字で区別し、押したら確認を出す。
- 発表を始めると、まず参加の画面（QR コード、リンク、参加人数）が出る。「QR コード」ボタンで、授業の途中でも重ねて出せる。
- アンケートスライドでは、質問と選択肢に加えて次を出す。
  - 状態の表示: 「受付中」「受付停止中」「締切済み」（色だけでなく文字で）。
  - 回答数（「回答 18 人 ／ 参加 30 人」）。回答数は結果の非公開中も出す。
  - 「結果を表示」／「結果をかくす」: 結果（選択肢ごとの棒、件数、割合。分母は「回答した人数」と明記）を出し入れする。「すぐ表示」の質問では最初から出ている。
  - 「受付を止める」／「受付を再開」: 締切前だけ押せる。結果の表示とは別の操作。
- 「次へ」で次のスライドに進むと、今のアンケートは締切済みになる。「前へ」で戻ると「締切済み」と出て、受付の操作は押せない。結果の表示・非表示は切りかえられる。
- 先生が発表画面を閉じたり再読み込みしたりしても、開き直せば同じ授業の同じスライドから続けられる（ダッシュボードに「発表中の授業に戻る」を出す）。

### 5.5 生徒の画面

要件定義書 7.6 D をもとにする。縦 1 列。

- 上部: 授業名、通信状態（「接続中」「接続が切れています。つなぎ直しています」）。
- 資料スライド: スライドを画面の幅いっぱいに出す。生徒がスライドを前後に動かす操作は置かない。
- アンケートスライド: 質問文、「この質問は匿名です」、選択肢のカード（高さ 56px 以上。A〜F の記号と文）、「回答を送信」。名前の欄は出さない。
  - 選択肢を押すと「選択中」になる（まだ送っていない）。「回答を送信」で送り、サーバーが受け取ったと確認できてから「送信済み」と出す。
  - 送信済みのあとで別の選択肢を選ぶと、ボタンは「回答を更新」になる。
  - 状態: 送信中／送信済み／一時保存（つながったら送ります）／送信できませんでした／受付停止中／締切済み。
  - 結果: 先生が結果を表示している間だけ、発表画面と同じ棒グラフを出す。
- 先生が授業を終了すると、終了画面（「授業は終了しました」）になる。
- 授業 ID がまちがっている、または終了済みのリンクを開いたときは、その旨を出す。

### 5.6 授業履歴と結果

- 授業履歴: 終了した授業の一覧（教材名、実施日時、参加人数）。
- 結果: 質問ごとに、選択肢別の件数と割合、回答した人数。個人ごとの一覧は出さない。授業の記録の削除（確認つき）。

## 6. データ

### 6.1 データベースの構造

```
teachers/<先生のuid>/
  decks/<教材ID>/
    title, updatedAt
    order: [スライドID, ...]
    slides/<スライドID>/
      type: "content" | "poll"
      content の場合: items: [{ kind:"text"|"image", x, y, w, h, ...}]
      poll の場合: question, options:[文...], resultMode:"live"|"manual"
    images/<画像ID>: データ URL（JPEG）
  history/<授業ID>/      … 終了した授業の記録（教材名、日時、参加人数、質問ごとの集計）

sessions/<授業ID>/
  owner: 先生のuid
  pub/                   … 生徒に見せるもの（生徒はここを 1 本の接続で受け取る）
    title
    state: "live" | "ended"
    current: { slideId, index }
    polls/<スライドID>/
      status: "waiting" | "open" | "paused" | "closed"   … waiting はまだ出していない質問
      resultsVisible: true | false
    results/<スライドID>: { counts:[...], total }   … 公開中だけ先生の端末が書く
  deck/                  … 発表を始めたときの教材の写し（スライドと画像）
  inbox/                 … 生徒から届くもの（先生だけが読める）
    participants/<生徒のuid>: 時刻
    answers/<スライドID>/<生徒のuid>: { choice, at }
```

（2026-11-11 計画を書くときに更新: 無料枠の同時接続 100 を節約するため、生徒に見せるものを `pub`、生徒から届くものを `inbox` にまとめた。下の 6.2〜6.4 の `current`・`polls`・`results`・`state` は `pub` の中、`answers`・`participants` は `inbox` の中を指す。教材の一覧用に `teachers/<uid>/deckIndex`、発表中の授業の印に `teachers/<uid>/active` を足した。）

- 授業 ID は、推測できない長さのランダムな文字列（20 文字以上）。これが参加リンクになる。
- 発表を始めるとき、教材を `sessions/<授業ID>/deck` に写す。授業中に教材を編集しても、進行中の授業は変わらない。
- 画像の位置や大きさは、キャンバスに対する割合（0〜1）で持つ。端末の画面の大きさが違っても同じ配置になる。

### 6.2 規則（だれが何を読み書きできるか）

- `teachers/<uid>` 以下は、その先生だけが読み書きできる。先生として登録されているかどうかは、`teacherList/<uid>: true`（管理者がコンソールで書く。アプリからは書けない）で判定する。
- `sessions/<授業ID>` を作れるのは登録されている先生だけ。`deck`、`current`、`polls`、`results`、`state` を書けるのは `owner` の先生だけ。
- 生徒（匿名ログイン）は、`deck`、`current`、`polls`、`results`、`state`、`title` を読める。授業 ID を知らないと読めない（一覧は取れない）。
- 生徒は `answers/<スライドID>/<自分のuid>` だけを書ける。条件は、授業が `live`、その質問が `open`、`current.slideId` がそのスライドであること。**ほかの生徒の回答は読めない。** `answers` を読めるのは `owner` の先生だけ。
- 生徒は `participants/<自分のuid>` だけを書ける。

### 6.3 結果の公開のしかた

生徒は `answers` を読めないので、結果は先生の端末が集計して `results/<スライドID>` に書く。

- 結果を表示している間: 回答が届くたびに（0.5 秒に 1 回まで）集計を書きなおす。
- 結果をかくしたとき: `results/<スライドID>` を消す。
- これで、非公開の間は生徒の端末に集計が届かない（画面でかくすだけでなく、データとして届かない）。

### 6.4 回答の数え方と締切

- 回答は `answers/<スライドID>/<生徒のuid>` の 1 か所に上書きする。変更しても件数は増えない。
- 「次へ」を押したとき、先生の端末は「今の質問を `closed` にする」と「`current` を次のスライドにする」を 1 回の書きこみで行う。
- 締切後に届いた回答は規則が拒否する。生徒の画面には「締切済みのため送信できませんでした」と出す。
- 授業の終了: `state` を `ended` にし、開いている質問をすべて `closed` にし、集計を `teachers/<uid>/history/<授業ID>` に保存する。以後、生徒は参加も回答もできない。`sessions/<授業ID>` の `answers` と `participants` は、保存のあとに消す。

### 6.5 通信が切れたとき（試作1 の範囲）

- 生徒: 読み込み済みのスライドはそのまま見える。回答は端末（localStorage）に一時保存し、つながったら自動で送る。そのとき質問がまだ `open` なら集計に入る。すでに締切済みなら入らない（その旨を出す）。
- 先生: つながっていない間は「前へ」「次へ」を押せない（生徒の画面とずれるのを防ぐ）。状態を文字で出す。
- 要件定義書 4.8 の「締切前と確認できる後着回答を集計へ加える」は、試作1 では行わない。締切前だったことを確かめる方法が決まっていないため（要件定義書 10 章の論点）。段階 5 で扱う。

## 7. 匿名性について（試作1 の扱いと、残る論点）

- 試作1 の回答はすべて匿名。名前を入力する場所がなく、先生のデータにも名前がない。
- 回答には端末ごとの匿名の ID が付く。同じ授業の中で、同じ端末の回答どうしは同じ ID になる（回答の変更と、二重に数えないために使う）。先生の画面にはこの ID を出さず、授業の終了時に集計だけを残して ID ごとの回答を消す。
- ユーザーの決定（2026-11-13）: 記名回答（名前つきの回答）は作らない。回答はすべて匿名のままにする。下の論点は、今後もし作ることになった場合のために残す。
- 残る論点: 段階 2 で記名回答を足すとき、同じ ID のままだと、記名の回答と匿名の回答を照合できてしまう。段階 2 の設計で、質問ごとに別の ID を使う方法を決める（要件定義書 10 章「匿名性と回答更新」）。

## 9. 確かめ方

- 自動テスト（`npm test`）: データの検査、順番変更、進行と締切（次へ・前へ・停止・再開・終了）、集計（上書きで件数が増えない）、未送信回答の再送、規則のファイルの形。
- 規則の確認: Firebase のコンソールの「ルール プレイグラウンド」で、生徒が他人の回答を読めない・書けない、締切後に書けない、ほかの先生の教材を読めないことを確かめる。手順を `docs/firebase/setup.md` に書く。
- ブラウザでの確認: 先生 1 つと生徒 2 つ以上のタブを開き、要件定義書 7.8 の表（回答を送る、締切前に変更、次へ、前へ、通信断から復旧、授業を終了）を順に確かめる。iPad の幅（縦 768px、横 1024px）で文字切れがないことを見る。
- 授業の前の確認: ユーザーが学校の iPad 数台で参加から終了までを通す。
- 要件定義書 7.9 の見やすさ: 文字のコントラスト比 4.5:1 以上、主要なボタン 44×44px 以上、200% 拡大で主要操作が使えること、キーボードで操作できることを確かめる。
