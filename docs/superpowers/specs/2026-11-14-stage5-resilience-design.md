# 段階 5: 30 人での負荷の確認と、通信が切れたときの強化の設計書

- 作成日: 2026-11-14
- もとになる設計書: `2026-11-11-classpulse-design.md`（段階 5、86 行・224 行・277 行）
- 要件定義書の項目: 4.8、176 行（フォントを通信断でも使う）、254 行（通信断から復旧）、280 行

「ユーザーの決定」は先生が決めたこと、「Claude の判断」は Claude Code が決めたことである。

## 1. 目的と前提

- **ユーザーの決定:** 段階 5（30 人が同時に使うときの負荷の確認、通信が切れたときの強化）に進む。（200 人は対象にしない。1 学級 30 人が前提。）
- Claude Code は、本物の Firebase にログインしない決まりなので、本物での 30 人の試験はできない。このため、(a) 手元でのシミュレーション、(b) 数字の見つもり、(c) 先生が本物で行うリハーサルの手順、の 3 つで確かめる（Claude の判断）。
- 今のコードを読んで見つけた弱い所を直す。下の中身は、すべて Claude の判断である。

## 2. 今のしくみで見つけた弱い所

1. **止まった受信に気づけない。** 変化の受信（`net.subscribe`、EventSource）は、Wi-Fi が不安定なとき、エラーを出さないまま止まることがある。今は、エラーが出たときしかつなぎ直さない。生徒の画面が古いスライドのまま「接続中」と出つづける。
2. **端末がスリープから戻ったとき・通信が戻ったときに、すぐつなぎ直さない。** iPad は、画面を消すと受信を止めることがある。戻ったときは、次のエラーが出るまで待つことになる。
3. **参加のときの失敗が、手で「もう一度」を押すまで戻らない。** 30 人がいっせいに QR コードを読むと、何人かは通信に失敗しうる。今は、失敗するとすぐ「通信できませんでした」になる。
4. **通信が切れている間にページを読みこみ直すと、白い画面になる。** アプリの部品を端末に残していないため。送れていない回答は端末に残っているのに、画面が出ない。
5. 30 人が同時に答えたときの、先生の端末の集計の重さと、書きこみの回数を、数字で確かめていない。

## 3. 作るもの

### 3.1 受信の見張り（`js/net.js`）

- `subscribe` ごとに、最後にイベント（`open`・`put`・`patch`・`keep-alive`）を受けた時刻を持つ。
- `CONFIG.streamStallMs`（75000）の間、何も受けなければ、止まったとみなす: `status('disconnected')` を出し、接続を閉じて、すぐつなぎ直す（トークンは取り直さない。失敗したら今までの再試行に入る）。
  - Firebase は、変化が無い間も `keep-alive` を送る。間隔は公式の資料に書かれていない（実際は 30 秒ほど）。75 秒は、2 回分を待つ長さ。
- 見張りのタイマーは、解除（`unsubscribe`）で必ず止める。時計とタイマーは引数で受け取る（テストできる形）。
- つなぎ直すと、Firebase は最初にその場所の全体を `put` で送る。今の `handle` がそれで値を置きかえるので、止まっていた間の変化も取りこめる（今の動きのまま）。ただし、つなぎ直しの最初の `put`（`path` が `/`）では、古い値に重ねず、置きかえること（今もそうなっているか確かめ、テストで押さえる）。

### 3.2 戻ったときのつなぎ直し（`js/net.js`、`js/main.js`）

- `createNet` の返す物に `wake()` を足す。呼ばれたら、開いている `subscribe` のうち「つながっていない」か「最後のイベントから `CONFIG.streamWakeMs`（10000）以上たっている」ものを、すぐつなぎ直す（再試行の待ちの最中なら、待たずに今つなぐ）。それ以外は何もしない。
- `main.js`: `window` の `online`、`pageshow`（`persisted` のとき）、`document` の `visibilitychange`（見える状態になったとき）で、先生用・生徒用の `net.wake()` を呼ぶ。練習モードの net に `wake` が無ければ呼ばない。
- 続けて何度も呼ばれても、同じ接続を何度も作り直さない（つなぎ直しを始めたら、その接続が開くか失敗するまで、`wake` はその `subscribe` に何もしない）。

### 3.3 参加の自動のやり直し（`js/session-client.js`、`js/views/student.js`）

- `start()` の中の、匿名ログイン・`pub` の読みこみ・教材の読みこみ・参加の書きこみが、通信の失敗（`NetError` の `network`・`unknown`）で止まったら、自動でやり直す。3 回まで。待ち時間は 2 秒・4 秒・8 秒に、0〜1 秒の乱数を足す（30 人が同じ時刻にやり直さないように）。
- やり直しの間、状態は `phase: 'loading'` のまま、`retrying: n`（何回目か。1〜3）を持つ。生徒の画面は「つなぎ直しています…（n 回目）」と出す。
- 3 回やり直しても失敗したら、今までどおり `phase: 'error'`（「通信できませんでした。」「もう一度」）。「もう一度」を押したら、回数は最初から。
- やり直さないもの: 授業が見つからない、もう終わっている、規則に拒否された（`denied`）、ログインが無効（`auth`）。今までどおりの画面にする。
- 画面を離れたら（`stop()`）、待ちを止める。待ち・乱数は引数で受け取る（テストできる形。既定は `setTimeout`・`Math.random`）。
- 成功したあとの動きは、今までと 1 つも変えない。

### 3.4 部品を端末に残す（Service Worker。新しい `sw.js`、`js/main.js`）

- 目的は 1 つ: **通信が切れている間に読みこみ直しても、アプリの画面が出るようにする。** 速くするためには使わない。
- しくみ（ネットワーク優先）:
  - 同じ場所（同じ origin）の GET だけを扱う。Firebase・Google への通信、ほかの origin、GET 以外には、何もしない（`respondWith` を呼ばない）。
  - まずネットワークから取る（`cache: 'no-cache'` で、ブラウザの古い写しを使わせない）。成功（200）したら、その写しをキャッシュに入れて返す。**ネットワークで取れたら、必ず新しい方を使う。**
  - ネットワークが失敗したときだけ、キャッシュの写しを返す。ページの移動（`navigate`）で写しが無ければ、キャッシュの `index.html` を返す。
  - 200 でない応答・部分の応答（206）・`opaque` の応答はキャッシュに入れない。
  - キャッシュの名前は `classpulse-v1`。`activate` で、名前のちがう古いキャッシュを消す。`skipWaiting` と `clients.claim` を使う（新しい sw.js がすぐ効く）。
  - 最初に入れておく一覧（プリキャッシュ）は作らない（一覧の更新もれで古い部品が残る事故を作らない）。1 回開いた画面の部品だけが残る。
- 登録（`js/main.js`）: `https:` で、練習モードでなく、`navigator.serviceWorker` があるときだけ、読みこみが済んだあとに `register('sw.js', { updateViaCache: 'none' })`。失敗しても何もしない（アプリはそのまま動く）。`localhost`・`127.0.0.1` では登録しない（開発中に古い部品が残らないように）。
- `sw.js` は、リポジトリの一番上に置く（公開先の `/classpulse/` 全体を受け持つため）。`index.html` からは読みこまない。
- 生徒の未送信の回答・書きかけ・先生のログインは、今までどおり `localStorage` にある（Service Worker とは関係しない）。

### 3.5 30 人のシミュレーション（テストと道具）

- `tests/load.test.js`: 今ある練習用の通信（`js/dev/memory-net.js`）の上で、先生の host 1 つと、生徒の client 30 個を動かす。
  - 5 種類の質問（アンケート・クイズ・評価・自由記述・ワードクラウド）がある教材で、30 人が参加 → 全員が同じ時に回答 → 何人かが書き直す → 次へ → … → 終了。
  - 確かめること: どの質問も回答が 30（二重に数えない）、履歴の人数・件数が正しい、参加人数が 30、公開する集計（`pub/results`）の書きこみが間引かれている（1 つの質問で、回答の数より十分に少ない）、どの client も最後に同じスライド・同じ状態を見ている。
  - 途中で 5 人の受信を切って戻す（memory-net にその手段が無ければ、テスト用の包み（net を包んで `subscribe` の通知を止める・失敗させる）を `tests/helpers/` に作る）。戻ったあと、未送信の回答が届き、今のスライドに追いつく。
- `tools/load-sim.mjs`: 同じ流れを、人数を変えて（既定 30。`node tools/load-sim.mjs 200` のように）動かし、数字を出す: 参加から終了までの処理時間、host の `onChange` の回数、`pub` への書きこみの回数、1 人の生徒が受け取る `pub` の変化の回数と文字数の合計、教材の写しの文字数。README には載せない開発用の道具。

## 4. 入れないもの（理由つき）

- 締切のあとに届いた回答を「締切の前に書いたもの」として数えること（全体設計 224 行）。端末の時刻は信用できず、規則で確かめる方法が無い。今までどおり、締切のあとの回答は数えない。
- 200 人への対応、接続を保たない方式（数秒ごとの読み直し）。30 人なら、同時接続は 32 ほどで、無料の枠（100）に収まる。
- 本物の Firebase に対して、機械で 30 人分の参加を作る道具（1 つの場所からのアカウント作成は 1 時間に 100 までで、試験でこの枠を使うと、そのあとの本物の授業で生徒が参加できなくなるおそれがある）。
- 先生の端末が切れている間の操作（次へ・結果を表示）を、ためておいて後で送ること（切れている間に押した操作が、戻ったときに急に効くと危ない。今までどおり、切断中は押せない）。

## 5. 数字の見つもり（報告書に書く。Claude Code が作る）

- 同時接続: 生徒 30（1 人 1 つ）＋ 先生 2（回答の受信と `pub`）＝ 32。無料の枠は 100。
- アカウント作成: 生徒は、はじめて使う端末で 1 回だけ匿名のアカウントを作る（端末に残るので、次の授業からは作らない）。Firebase の決まりは「1 つの IP アドレスから 1 時間に 100 まで」。学校は 1 つの IP アドレスにまとまることが多いので、**はじめて使う日に、同じ 1 時間のうちに 4 学級以上が使うと、枠をこえるおそれ**がある（匿名の作成がこの数に入るかは、資料に書かれていない。入るとみて備える）。Firebase の画面で、日時を決めて一時的に枠を広げられる。
- 通信量: 教材の写し（最大 5MB ほど）× 30 人が、参加のときに 1 回。これは今までの記録のとおり。

## 6. 確かめ方

- 自動テスト: 受信の見張り（75 秒で切ってつなぎ直す、`keep-alive` で延びる、解除で止まる）、`wake`（つながっていない物だけ・古い物だけ・連打）、つなぎ直しの最初の `put` で置きかわる、参加のやり直し（1 回目で成功・3 回目で成功・4 回とも失敗・やり直さない種類・待ちの最中に `stop`）、Service Worker の決めごと（純粋な関数に分けてテスト: どの要求を扱うか、何をキャッシュに入れるか）、30 人のシミュレーション。
- ブラウザ（練習モード）: 今までの流れが変わらないこと。生徒の画面の「つなぎ直しています…」。
- Service Worker は、`localhost` では登録しないので、公開先で Claude Code が確かめる（ログインのいらない画面で、登録されること・通信を切って読みこみ直しても画面が出ること）。
- 本物の 30 人: 先生がリハーサルの手順（報告書に書く）で確かめる。

## 7. 知っている限界

- 受信が止まってから気づくまで、最大 75 秒かかる（その間は、古いスライドのまま）。画面を消して戻したとき・通信が戻ったときは、すぐつなぎ直す。
- Service Worker が部品を残すのは、1 回開いた画面の分だけ。はじめて開く端末は、通信が無いと開けない。
- 通信が切れている間は、回答は端末にたまり、つながったら送る。その間に締め切られた回答は、数えない（今までどおり）。
- Service Worker のある端末でも、通信がつながっていれば、いつも新しい部品を取りに行く（古いアプリが残ることはない設計。ただし、通信が切れている間は、前に開いたときの部品で動く）。
